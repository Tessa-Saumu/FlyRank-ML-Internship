Every term used in this paper, defined once

  • Page: one piece of content on one client's site. Pages and clients appear only as scrambled codes. Nothing client-identifying is in the data.
  • Impressions: how many times a page appeared in Google search results in a 30-day window. Clicks: how many of those became visits.
  • CTR: clicks divided by impressions, as a percentage. A CTR of 0.76 means 0.76%, not 76%.
  • Position: the page's average rank in Google results. 1 is the top.
  • Decline: the label. A page's impressions in the next 30 days fall below 80% of its impressions in the last 30 days.
  • Base rate: the share of all pages that declined. Any ranking must be read against it.
  • Precision@50 (P@50): of the 50 highest-ranked pages, the share that really declined. This is the metric, because the budget is 50 reviews a month.
  • The rule: the hand-written baseline. A transparent score built from three yes/no conditions. It uses a 500-impression visibility cut.
  • Entry floor: the Week 3 data contract. A page needs 100 impressions and 14 days of data to enter the table at all. This is not the rule's 500 cut. Both numbers are used. They do different jobs. Section 2.
  • LR / RF: logistic regression and random forest, the two models compared against the rule.
  • Frame: one table, one row per page: a feature month plus the next month's outcome. March frame means March features and April outcomes.
  • Receipt: a committed JSON file of numbers produced by an executed notebook. Every headline number in this paper traces to one, or to a table that notebook printed.

Abstract

When a content team can review only 50 pages a month, the practical question is which 50 should go first. We built one table per month from FlyRank's anonymized internship warehouse, about 79 million daily rows, and the March working table holds 95,810 pages across 40 clients, each with five numbers known at month-end and a label for whether next-month search impressions fell by 20% or more. On those five numbers we trained logistic regression and a random forest, and we compared both with a hand-written rule under a client-grouped split, a one-month-forward test, and a planted leak. Measured across five client-grouped folds, mean precision@50 was 0.636 and 0.608 versus 0.512 for the rule, against a 0.49 base rate; one month forward the edge mostly disappeared (0.54 versus the rule's 0.44 and a 0.56 base rate; random forest 0.14), and a random split that reuses clients scored 0.98, which we treat as leakage, not skill. The shipped output is a 50-row monthly review order for a human editor, with a plain reason per row and a fall-back to the rule: decision support for which pages to inspect, with no claim that reviewing or changing a page changes its traffic.

What this paper claims

Four claims. Each one points at the section that carries it. The words are the four this track allows: observed, measured, directional, decision support.

  1. On the five-fold means, both learned models ranked the review queue above the hand rule: precision@50 of 0.636 (logistic regression) and 0.608 (random forest) versus 0.512, against a 0.49 base rate. Fold by fold, logistic regression is below the rule on fold 1, and the random forest ties the rule on two folds. The mean advantage is real. A win on every fold is not. Section 4.
  2. The advantage is short-lived. One month forward, logistic regression stayed above the rule (0.54 vs 0.44) but did not beat picking at random (base rate 0.56). The random forest fell to 0.14. Adding up to four months of training history did not restore the edge. Section 4.
  3. The way the data is split can fake skill. On a naive random split the random forest scored 0.98 because 34 of the 40 clients landed on both sides. It was re-describing pages it had already seen, not forecasting. Section 4.
  4. The deliverable is a gated review queue, not a forecast: 50 rows, each carrying a model score for order, a rule flag for the reason, and one of four actions. Hard limits say what is never automated. If the model falls behind the rule for two labelled months, ordering goes back to the rule. Section 6.

1Introduction and problem statement

Search traffic to a page usually slides. By the time a monthly report looks bad, the drop has often been underway for weeks. A content team that manages many sites therefore has one standing question: of all the pages we could look at this month, which 50 should a person actually spend time on? The budget is fixed at about 50 reviews a month. The value is in the order at the top of the list, not in the average quality of a score across a hundred thousand pages.

There is already a sensible hand answer. Old pages decline more often than newer ones. Pages that rank near the top of Google results while hardly anyone clicks them are the usual refresh candidates. The Week 4 baseline encodes that intuition in a transparent three-condition score. The problem is that the score is blunt. In the March 2026 working table, 24,462 pages tie at the rule's maximum score. "Top 50 by the rule" is a draw from that tie, and the band's own decline rate is 50.7%, barely above the month's 49.1% base rate.

A model was trained to do the one thing the rule cannot: order that tie, and the pages around it, using five numbers per page. "Did the model beat the rule" turned out to be the wrong question on its own. The answer depends on how the comparison is run. This paper runs the same three scorers (the rule, logistic regression, and a random forest) under three tests, ending with the test that matches deployment: trained on one month, scored on the next.

The cost of a wrong call is uneven, and worth naming. A wasted review uses about an hour of a 50-hour monthly budget. A missed decline leaves a page to decay for another month. Neither is catastrophic. That is why this is decision support for a human, not an automation.

2Data

Source and scale

All data comes from the FlyRank ML Internship warehouse release, hosted (gated) at FlyRank/internship-warehouse on Hugging Face. It is about 79 million daily rows, covering late 2025 through 30 June 2026, read with DuckDB and never downloaded in bulk. The release is already public-safe by construction: no client names, domains, URLs, page titles, or search queries exist in it. Pages and clients appear only as scrambled codes, used here for joining and grouping, never as model inputs.

Three tables were used: fact_content_daily_performance (one row per page per day of search performance), dim_content (page metadata, including creation date), and dim_clients (client context). The query-level table was excluded because its fixed 90-day window can overlap the outcome month, which would let future information into the features.

Two impression cuts, two jobs

Read this before the word "floor"

This project uses two different impression cuts. They are both in the notebooks. They are not substitutes for each other. The 100 is who is allowed into the table. The 500 is who the hand rule calls visible.

CutNumberWhere it was setWhat it does
Entry floor At least 100 impressions and 14 days of data in the feature month, and 14 days of data in the outcome month Week 3 data contract. Every later notebook copies this filter in SQL: recent30_impressions >= 100 Who enters the modeling table at all. Below that, CTR and position are noise on a tiny denominator, and one quiet day can look like a decline.
Visibility cut At least 500 impressions Week 4 hand rule: visible = impressions >= 500. Week 5 left this cut untouched on purpose. Who the rule has something to say about. The stale and low-CTR checks apply only to these pages. Pages with 100 to 499 impressions stay in the table and are flagged low_visibility.

Changing the entry floor from 100 to 500 would rebuild every frame and every number in this paper. That is a different experiment. It was not run. The 95,810-page March table is the 100-impression table.

Who is in, who is out, and why

  • Entry floor, applied upstream: 100 impressions and 14 days in the feature month, plus 14 days of outcome-month coverage. This is the Week 3 contract, not the rule's 500 cut.
  • Outcome-month tracking: the label needs the page to still be measurable next month. March kept 95,810 of 98,398 candidates, so 2.6% were dropped (391 with no outcome rows, 2,197 with thin coverage). April kept 99,279 of 102,943 (3.6% dropped). The bias points one way: pages whose tracking went quiet are excluded, so everything here describes pages that could still be measured.
  • Excluded fields: all future-window values (next-month impressions are the answer, not an input), label-derived trend fields, provider and model production metadata, and fixed-window query signals. The five features below are the complete input. Nothing else reaches the models.

The label

A page is labelled declining when its impressions in the next 30 days fall below 80% of its impressions in the last 30 days, and it has at least 100 recent impressions. The 80% line is a policy choice from the Week 3 contract. The printed sensitivity table in that notebook, not an earlier sentence above it, shows decline rates of 0.402 at 70%, 0.491 at 80%, and 0.571 at 90%. The 0.80 line was kept as the contracted threshold.

3Methodology

Assumptions, stated plainly

  • The label is a proxy (a 20% impressions drop), not a business outcome such as revenue.
  • At decision time (month-end), only that month's five numbers and the page's age are available. Those are the only inputs.
  • Review capacity, not scoring capacity, is the constraint: 50 pages a month.
  • The unit of analysis is the page. Clients matter only because their pages move together, which drives the validation design.

Features: the complete list

Five features, and only these, in every model and every test in this paper:

FeatureWhat it is
log_recent30_impressionsSearch impressions in the feature month, on a log scale
recent30_ctr_pctClicks divided by impressions, as a percentage
recent30_avg_positionAverage rank in Google results (1 = top). A raw 0 means no position data and is ignored before averaging.
recent30_active_daysDays in the month with impressions
content_age_daysDays since the page was created, at month-end

This list is the same one in the notebooks, the receipts, and this paper. Client and page codes are used to join tables and to group folds. They are never model inputs. The rule score is a baseline to beat, never an input.

The baseline rule

The Week 4 hand rule is a transparent weighted sum of three yes/no conditions, with no fitted weights.

  • Visible = at least 500 impressions. This is the visibility cut, not the 100-impression entry floor.
  • Low CTR in the top 10 = visible, average position 1 to 10, and CTR under 1%.
  • Stale = visible and at least 91 days old.

Score = 0.40 times visible + 0.35 times low-CTR-in-top-10 + 0.25 times stale. Each page also carries one of five reason codes: stale_low_ctr_top10, stale, low_ctr_top10, visible, low_visibility. That code is the plain-language "why" in the queue. low_visibility means under 500 impressions. The rule has nothing to say about those pages.

The Week 4 signal audit confirmed both intuitions, using the printed tables rather than an earlier sentence that quoted different percentages. Pages 91 days or older declined at 52.8% (65,503 pages) versus 41.1% for newer pages (30,307 pages). Among visible top-10 pages, CTR under 1% declined at 48.0% (35,710 pages) versus 17.1% for top-10 pages with CTR of 1% or higher (1,921 pages). A separate volume check (high volume = 500 or more impressions) was mixed: high-volume pages did not decline more often. The 500 cut is an editorial choice, not a finding that more impressions means more risk.

Models

Two standard classifiers, kept simple, with library-default settings and no tuning: logistic regression (features standardized inside the training pipeline, so test-fold statistics never leak into training) and a random forest. Both output a probability of decline. That probability is the ranking score. Random seed 42 everywhere.

Validation design: the fair-test contract

Model and baseline are always evaluated under identical conditions: the same eligible rows, the same folds, the same metric (precision@50), and the same tie-break (impressions, highest first). Three tests, one question each:

  • Test A, random split (the trap). A plain 80/20 row split. Clients land on both sides. It answers: how good does the model look when it is allowed to re-describe pages it has already seen? Run on purpose, as a check on honesty.
  • Test B, client-grouped, five folds. Five draws, each holding out about a quarter of the 40 clients. Zero clients shared per fold. That overlap is asserted in code and recorded per fold in the receipts. It answers: can the model rank pages for a client it has never seen?
  • Test C, one month forward. Fit on the March frame, score the April frame, nothing retrained. It answers: does the ranking survive the month between training and use? That is exactly how the queue is deployed.

A fourth test, walk-forward with growing history, asks whether Test C's drop is only a "trained on one month" artifact. The test side stays fixed on April. The training set grows from one to four monthly frames. The clients are restricted to those present in every frame, so the panel does not change under the model.

Leakage checks

  • Timeline drawn: features end strictly before the label window opens. This is asserted at build time for every frame. March features run 2 Mar to 31 Mar. The label runs 1 Apr to 30 Apr. One day of separation.
  • No label-derived features: the models see exactly the five contracted columns. Trend fields and future fields never enter.
  • No product flags: the rule's score is a baseline to beat, never an input.
  • IDs group, they do not learn: client and page codes are used for grouping folds and joining tables only.
  • Population checked: the outcome-month join was audited and its exclusion rates measured (Section 2).
  • The check itself was tested: a known leak, the label's own column, was planted in the feature matrix. Average precision jumped from 0.761 to 0.993. An audit that cannot catch a planted leak cannot clear an honest one. The column was removed. Every number in this paper uses the honest five.

This model is predictive, not causal. It does not prove that any feature is a search-ranking factor, and it does not prove that reviewing or changing a page will cause traffic to recover. The spread deserves as much attention as the means. The rule's fold scores wander from 0.32 to 0.84 because its top 50 is an arbitrary draw from a 24,462-page tie band whose underlying decline rate is 50.7%. The models break those ties. That is their job. Fold-to-fold client mix still moves everything. The audit measured 829 rows in the March frame with identical feature values, and in the strongest fold the random forest's top 50 came from just 3 of the 10 test clients (112 frame rows carry a probability above 0.9). The paired difference of random forest minus logistic regression is -0.028, with a standard deviation of 0.059. That is inside fold noise. The two models are not separable on five folds. Logistic regression is kept as the readable companion, and it is the score used to order the deployed queue.

Test C and the walk-forward: the edge is good for one cycle

Fit on March and scored on April, the random forest's precision@50 falls to 0.14 against a 0.56 base rate. Logistic regression holds 0.54, above the rule's 0.44 but not above picking at random. Logistic regression does keep some global ordering (average precision 0.624 versus the rule's 0.559). The head of the list is what a 50-slot budget spends, and at the head the lift is gone. On the full panel, the base rate itself moved from 0.200 in February to 0.560 in April, so the model was also aiming at a moving target.

What the models actually learned

Permutation importance, measured on a held-out fold, puts CTR first. Shuffling it drops average precision by 0.080, about 2.8 times the drop from shuffling the next feature, active days (0.028). After those two come content age (0.021), log impressions (0.012), and position (0.009). The clearest interpretation mistake a straight-line model can make showed up on schedule: logistic regression's age coefficient came out negative (-0.15) even though staleness is a confirmed signal, because decline risk does not rise in a straight line with age. The measured shape, in the April frame:

The models' most confident mistakes repeated one pattern across weeks: pages ranked 1 or 2 in Google results with near-zero CTR (0.07% to 0.18%) on thousands of impressions, many from a single client. That is usually not decay. It is a results page that answers the search itself, or a search for the brand's own name. Rewriting the page cannot fix either. That pattern is now a gate in the playbook (Section 6), not a lesson re-learned monthly.

5Limitations and honest framing

What this work cannot claim, written here before a reader has to write it:

  • Not causal. No page was experimentally changed. Nothing here shows that reviewing, refreshing, or rewriting a page affects its traffic in either direction. The queue orders risk. It does not promise that acting on it prevents anything.
  • Short shelf life. The ranking is good for one cycle: stronger in the month it is fit, near chance one month forward (Test C), not rescued by more history (Table 4). Every recommendation in Section 6 follows from this.
  • The label partly measures measurement. Pages with only 14 to 20 days of tracking in the outcome month declined at 96.2% (3,485 pages), versus 39.8% for pages covered all 30 days (70,253 pages). Some "declines" are gaps in tracking, not drops in demand.
  • Survivorship. 2.6% of March candidates and 3.6% of April candidates were dropped for thin or absent outcome-month tracking, and those lean toward pages going quiet. This paper describes pages that could still be measured.
  • Client concentration cuts both ways. The largest client is 22% of a frame. 829 frame rows share identical feature values. In the current cycle one client holds 48% of the budget queue, and the monitoring clock flagged that against a 35% limit. Fold means are five draws of unequal, correlated data. Fold 3's test side alone is 70.6% of the frame (67,657 of 95,810 rows). These are not five independent experiments.
  • Five numbers cannot see content. Quality, search intent, the layout of the results page, seasonality, and business value are invisible to the features. A human reviewer sees all of them. That split of work is the point of the design.
  • One development month for the headline comparison. Test B lives on March 2026. The walk-forward test covers more history, but on a smaller fixed panel of 20 clients.
  • Untuned defaults. Both models run library-default settings. Tuning might move the numbers. It would not change the shape of the story, and it was deliberately not chased.
  • Earlier sentences in the notebooks do not all match the printed tables. Where they disagree, this paper follows the printed table or the committed receipt. The disagreements that matter are named next to the number they affect: the two impression cuts, the label-threshold sensitivity rates, the Week 4 signal rates, and the "won every fold" sentence.

The claim this paper stands behind

Observed across five client-grouped folds in March 2026, both learned models ranked the review queue above the hand rule on the five-fold means (0.636 and 0.608 versus 0.512, base rate 0.49). Measured one month forward, the lift at the head of the queue mostly disappeared (0.54 versus a 0.56 base rate). The models are directional decision support for choosing which pages a person reviews. Refit them monthly, check them against the rule, and never read them as a forecast or a causal argument.

6Ranked recommendations: the action playbook

The output is a monthly review queue, built the way Test C validated it: models fit on March, scoring April. The rule explains. The model orders. Each of the 50 rows carries the scrambled page code, the model probability (the order, tie-broken by impressions), the rule flag (the reason), one of four actions, and a refresh hint pointing at the kind of work the features suggest.

Who uses it: a content lead or editor running a monthly refresh sprint across many client sites. When: rebuilt on the first working day of the month from the previous month's numbers, with the model refit on the last month that has labels. A queue older than its feature month is expired. Budget: exactly 50 pages, which is why the metric is precision@50.

The four actions

review_before_revert
The default. Look at the page. Look at what people searched for when they found it. Write down a hypothesis. Then change content. Never change a page on the score alone.
verify_then_review
Impressions moved more than 7 times month over month, in either direction. A jump that big is more often a tracking or analytics change than a demand change. Check that first.
monitor_only
Impressions at least 1.5 times last month. The page is rising. Do not touch it. Whether the rise lasts needs a second month. This is a one-month test, and it is disclosed as such.
investigate_quiet_risk
Model probability at or above 0.70, but the rule flag is not a risk flag. The model sees something it cannot explain. A person checks. This cycle, 49 of the 50 queued rows are this action.

What this cycle's queue actually was

All 50 rows are pages the rule does not flag. The rule flag on every row is low_visibility, which means under the 500-impression visibility cut. They are in the table because they cleared the 100-impression entry floor. The printed head of the queue is small pages, about 100 to 180 impressions. The Week 7 write-up records zero measured clicks on that head. Observed against April labels, the ungated top 50 declined at 0.54 (base rate 0.56). After gates, the rate is 0.56, exactly the base rate.

This month the queue is a diagnostic list, not a refresh list: 49 quiet-risk investigations and 1 verify-then-review, about 49.5 editor-hours in total, with about 4,800 impressions at stake on those rows (4,706 on the quiet-risk rows and 92 on the verify row). That is the model behaving as trained. Zero clicks at a visible position is a strong pattern it learned. It is also why the queue is framed as a review order and not a forecast.

The ranked actions, in order

  1. Cap per-client share of the queue before it goes to editors. One client holds 48% of this cycle's top 50 against a 35% limit. The concentration trigger fired. A per-client cap is a policy decision for whoever runs the sprint. Until it is set, the list is not ready to hand out.
  2. Use the queue as a review order, with the checklist. For every row: what people searched for, what the results page looked like, technical state, seasonality, business value, and sensitive-topic routing (health, money, legal, and safety pages go to subject-matter owners). The reviewer writes one of act, defer, not_actionable, or escalate. Those decisions are worth more than another month of impressions, and they are the labels a future model should learn from.
  3. Refit monthly. Retire any queue older than its feature month. Test C and Table 4 are the evidence. An old queue is not a slightly worse queue. Near the front it is close to a random list.
  4. Keep the fall-back armed. If the model's precision@50 lands below the rule's for two consecutive labelled months, ordering reverts to the rule until a refit beats it again. This cycle: logistic regression 0.54 versus the rule 0.44, so the fall-back is not triggered. The stricter check (the model must clear the base rate by 0.05) did trigger (0.54 versus 0.61). It is reported rather than hidden.
  5. Watch the drift clocks. Before release, check feature stability with a population stability index (PSI: a score for whether a feature's distribution shifted since the model was fit). Position (0.108) and content age (0.179) sit in the "watch" band, under the act line of 0.25. Schema and base-rate drift checks passed (April versus March base-rate drift 0.069, under a 0.10 line). After release: label the queue when May outcomes arrive, and recompute precision@50 for the model and the rule on the same rows.
  6. Fix the data gap the gates exposed. An edit-history table would let the recently-edited lockout move from proposed to implemented, and would remove re-reviews of pages someone just improved.

The no-go list: never automated, whatever the score

  • No automated deletions, redirects, de-indexing, or page merges. Those are hard to undo, and the model has no idea why a page exists.
  • No unreviewed AI-written rewrites pushed live.
  • No automated edits to health, money, legal, or safety pages.
  • No bulk template or navigation changes triggered by page-level scores.
  • No client-facing promises built on this score. Precision@50 varies by about 0.2 between test splits.
  • No acting on monitor_only rows, and no rewriting rank-1 or rank-2 near-zero-CTR pages beyond checking which searches surface them.

How to rerun everything

  1. git clone https://github.com/Tessa-Saumu/FlyRank-ML-Internship and pip install -r requirements.txt.
  2. Request access to the gated dataset FlyRank/internship-warehouse (approval is instant). The warehouse is read with DuckDB straight from Hugging Face. There is no bulk download. Do not hardcode an access token in a notebook. The repo is public.
  3. Run the notebooks in order: w03_data_contract, w04_baseline_score, w05_model, w06_validation_audit, w07_action_playbook. Each writes its receipt to work/outputs/.
  4. python work/scripts/make_paper_figures.py regenerates every figure on this page from those receipts. capstone.ipynb re-checks each headline number against them. It does not need warehouse access.
  5. python work/scripts/deploy_paper.py publishes work/paper/index.html to the gh-pages branch. GitHub Pages serves that branch at the URL in submission/paper_url.txt.

Environment and seeds

  • Random seed 42 for every split, model, and figure.
  • Library versions of the committed run: pandas 3.0.3, numpy 2.5.1, scikit-learn 1.9.0, duckdb 1.5.4. These are recorded inside every receipt. Tree-based results can shift slightly between scikit-learn versions.
  • This page is a single self-contained file. Its source is work/paper/index.html. The five figures are embedded in it. Their source files live in work/figures/.

Public-safety pass

The data release contains no client names, domains, URLs, titles, or queries, only scrambled codes, and this page adds none. All results are aggregates. No row-level client data is published. Claim language throughout is observed, measured, directional, and decision support. There are no causal claims, and there is no claim that this work predicted Google's ranking algorithm.
